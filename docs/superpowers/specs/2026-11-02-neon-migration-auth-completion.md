# Kenkui migration admission and proof of legacy ownership

November 2, 2026. Controller-selected implementation contract for the [approved auth amendment](2026-11-02-neon-migration-design.md). Google and GitHub authenticate the person with Neon. A user-initiated mailbox challenge proves control of a particular old Kenkui account. It never grants a session or supplies general email sign-in. Preserve the exact restored UUID and all its owned books, jobs, balances and payment references.

## Public boundary

Ordinary verified session/resource access resolves existing bindings only. An authenticated, unmapped subject gets 409 `recovery_required`. Studio offers **Recover existing account** (including when the new social identity uses a different address) and **Create new account**. No automatic enrollment or challenge on lookup, resume, retry or provider callback.

| Explicit POST | Exact JSON object | Response |
|---|---|---|
| /v1/auth/onboarding | {} | 200 {userId}. A previously mapped subject returns its stable UUID. |
| /v1/auth/migration/challenge | {legacyEmail} | 202 {challengeId}, a random UUID for both eligible and ineligible well-formed hints. Copy: “If this address is eligible, check your inbox.” |
| /v1/auth/migration/verify | {challengeId,code} | 200 {userId} only after committed proof and linking. After an interrupted response retry the normal session lookup. |

All three require `authenticateRequest` with the new Neon Bearer, allowed mutation Origin, JSON-only strict fields, 2 KiB streamed cap and no-store responses. Invalid authentication is 401. Invalid proof, blocked decision or conflicting binding is sanitized 409 recovery_required; caller rate limit is 429 with Retry-After. Globally unavailable dependencies return 503 independently of mailbox. The address hint is never a delivery override. A public correlation ID cannot serve as an identity_link_proofs ID.

The separate Task 5 `/v1/auth/migration/link` accepts an actual verified WorkOS access JWT. Python `src/kenkui_server/auth/native.py:44–67` returns a *sealed session* under accessToken, including after refresh. `auth/browser.py:70–86` handles the browser cookie via WorkOS SDK load/authenticate/refresh. Neither supplies the raw JWT. Preserve the old desktop keyring slot for rollback and the distinct Neon slot; use these three public endpoints from both clients. Rust owns provider credentials and attaches the new Bearer. Neither a sealed string nor a returned old userId is proof for the JWT endpoint.

## Admission and selection

Use a narrow same-branch server projection from `neon_auth."user"`: `id` UUID, `email` text, `"emailVerified"` boolean, `banned` nullable boolean; match exact authenticated subject and canonical issuer. Every admission and recovery request needs a valid signed Neon token and a present current profile with banned IS NOT TRUE. Check those conditions again on proof consumption. A missing profile, invalid signature or active ban blocks recovery even if the submitted legacy proof is correct. New admission additionally requires a fresh, valid provider-verified email. For recovery the new address may be private, different or unverified; the proven mailbox is the server-known verified legacy address. No client profile, username or old users_sync field. Staging metadata and privilege checks confirmed the expected columns and schema USAGE/table SELECT for role `kenkui_owner`. Task 13 must confirm access as the deployed Function role and matching browser/native subject UUIDs. Provider-side Google/GitHub-only enforcement for current sessions remains a separate acceptance gate.

In a single transaction, return an existing binding or admit a genuinely new explicit request only with authoritative current email, ready directory, no owned legacy-address collision and the attested deployment policy. Insert the fresh server-verified Neon address into the new identities.email in the same transaction as account creation and provider binding, so NotificationStore.settings(userId) immediately reads it. Linking and idempotent retries preserve the existing email and notification preferences, even if the Neon profile address later changes. The old Python code always required verified email. `KENKUI_INVITED_EMAILS` defaults empty, and only a nonempty casefolded allowlist restricts verified users. Unknown deployed setting blocks admission, confirmed empty means open, confirmed nonempty requires membership. A unique source-only verified address has no old paid owner: allow deliberate new creation if otherwise eligible; never manufacture a WorkOS alias. Ambiguity (including a source-only record colliding with a different owned record) or any owned verified/unverified address blocks new creation. Never link by address. A different new mailbox cannot prove the person has no old account; explain the separate-account action and make recovery available first.

Only a unique, server-known, provider-verified old address with a nonnull mapped owner qualifies for email delivery. Unknown, source-only, ambiguous, unverified, duplicate candidate and blind owner-throttled hints all get the same 202 decoy behavior, with no mail. Neither passcode nor address can link a subject already bound to a different owner.

## Challenge, delivery and consumption

- Store random UUID, new canonical issuer/subject, active run/old owner/subject, code digest, creation/expiry, attempts, claim and consumption. Generate 16 uniformly random Crockford Base32 characters (80 bits); for verification remove ASCII spaces/hyphens only, uppercase ASCII, reject invalid alphabet/length. Digest is SHA-256 over ASCII `kenkui-migration-v1`, NUL, lowercase hyphenated challenge UUID, NUL, canonical code; compare constant-time. Ten-minute life and five wrong attempts. Never store plaintext codes.
- Durable transactionally serialized issuance limits for each new subject, including misses: 60-second cooldown, 3/rolling hour and 10/rolling day. Same caps per matched owner across subjects, suppressed behind generic 202. Verification: 60/rolling hour per new subject including unknown IDs and wrong-subject guesses. Charge guesses only against the rightful subject's challenge. Failed attempt/counter transactions must commit before raising a public error. An eligible resend supersedes only that same new-subject/owner pair. IP limits require trusted ingress evidence, never trust arbitrary forwarding headers.
- Assert global readiness before any address lookup: configured fixed Modal URL/proxy credentials/inner secret and the correct environment's usable SMTP configuration. Use a narrow protected POST `/migration-email/ready` with exactly {environment} returning {ready:true} or sanitized failure. Check sender config in Modal via the same factory used to deliver, no SMTP connection, DB lookup or secrets returned. Preflight failures uniformly return 503, including for decoys; misaddressed proxy, disabled bridge and missing sender are never per-target diagnostics. Real SMTP authorization/delivery needs separate owner receipt. Protect this readiness call with a bounded deadline.
- Social API durably commits challenge/limits first. Make at most one protected Modal POST `/migration-email` with **exactly {environment,challengeId,code}**, outside that transaction. Bound HTTP delivery wait to 1,500 ms; use the same minimum 2,000 ms response window on real/decoy/suppressed 202 paths measured from the same point. Already-claimed Modal work remains bounded and owned by existing bridge lifespan after HTTP abort/disconnect. A 202 promises no delivery. Keep an uncertain, possibly delivered code usable until expiry/supersession; explicit resend after cooldown. No new queue, automatic retry, waitUntil send or SMTP credential on Neon.
- In Python require existing Modal proxy auth, inner secret, correct environment, strict small wire models and a fixed message. In one short transaction claim once by UUID/digest/current run/expiry/unused state and re-resolve the eligible original delivery address from the server-owned directory. Commit and release DB before `SmtpMailer.send(Message(...))`. No recipient/subject/template/header override. The bridge already mounts the environment-scoped mail secret. Reuse `smtp_config_from_environment` and base mailer, without job preferences or unsubscribe links. No code/email/IDs in logs, traces, validation echoes or SMTP exceptions. A crash after claim may drop one send. If the credential cannot submit, its owner repairs the protected environment's existing mail setup.
- Verification and both identity paths share consistent locking. For an authenticated matching challenge use the same Postgres client and a single transaction to revalidate active directory/subject/owner/expiry, mint a short-lived existing-method `verified_legacy_email_challenge` proof, apply the Task 4 linker and mark proof and challenge consumed. An injected failure must roll back all effects. Never reassign a binding or alter credits, jobs, purchases or ownership. Never return a public proof ID. Daily bounded pruning removes expired challenges and expired rate records outside all relevant rolling windows; preserve directory metadata, one-use proof evidence, and all active jobs. No new timer or minute DB wake.
