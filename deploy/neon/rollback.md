# Rollback that retains Neon identities and current writes

The fallback is the **same TypeScript API** using the Hono Node adapter on Node24.21.0. It uses the same Neon issuer/JWKS/public client/resource, provider-to-internal UUID mapping and **current Neon database**. Do not deploy an old WorkOS-only Python image after Neon-only users exist. Never replace the current ledger/auth state with a pre-cutover dump.

## Prepared artifact

The reviewed manual release contains `standalone.tar.gz` (`standalone.js`, `package.json`) plus a manifest/file hashes and the corresponding Function archive. It has no runtime npm install or Python/core/Render dependency. `node standalone.js` binds `PORT` (default8080); on termination it stops new connections, allows10s drain, closes remaining SSE/download sockets and closes the shared DB pool. Client reconnection remains required. Function and standalone share the exact `src/index.ts` implementation, including lazy bootstrap, verified Neon claims, internal identity lookup, origin secret and bounded storage/event streams.

`deploy/neon/Dockerfile` builds the same fallback from the committed lock and a minimal final Node24 image as non-root. Use repository-root context with `docker build -f deploy/neon/Dockerfile .`; **Dockerfile-specific** `Dockerfile.dockerignore` allowlists only the build inputs. It does not change the legacy image's context. Local artifact/TLS/contract rehearsal is recorded in Task12 evidence; container execution and the real retained provider target remain Task13/operator gates unless separately demonstrated. No extra paid service is provisioned or kept warm merely for rollback.

## Emergency activation on an existing retained Render instance

1. Read the accepted manifest and select the exact reviewed server/Studio/core revisions and archive or image digest. Identify the **existing retained** same-environment Render service; verify its current plan, ownership and runtime before any mutation. A container image built from `deploy/neon/Dockerfile` or the two-file standalone artifact is suitable. The legacy `release-image.yml` image is not.
2. Pause new admission/webhooks and coordinate workers/schedules as required. Keep one authoritative writable Neon database. Deploy the fallback with `KENKUI_ENV`, explicit restricted **API** `DATABASE_URL`, the same `NEON_AUTH_BASE_URL`, `NEON_AUTH_JWKS_URL`, `KENKUI_NATIVE_CLIENT_ID`, `KENKUI_AUTH_RESOURCE`, allowed origins, origin secret, existing R2 salts/buckets, proper Modal proxy credentials and current Stripe settings. Reuse the reviewed API-only allowlist; never copy the provider's owner connection or a full env export. Do not change the API resource to Render's hostname: it stays the public API origin.
3. Keep `KENKUI_INGRESS_PROTECTION=true` and identical `KENKUI_ORIGIN_SECRET`. Before changing edge routing, check direct fallback missing/wrong origin secret403; through a private/local operator path, verify static catalog, a current Neon user's session/UUID/balance, upload rejection, SSE resume/cancellation and signed download. Preserve both old and newly created Neon identities. No real purchase is required.
4. Prepare the reviewed ingress config using `node release.mjs <environment> <existing-fallback-HTTPS-origin>` and dry-run it. This changes only the Worker upstream while keeping the public hostname and credentials scoped to one approved upstream; external redirects remain manual. Root/operator explicitly applies the named Worker/config only after the fallback is healthy. Record old/new origin, Worker version, API artifact SHA/digest, restricted role, current DB target and coordinated consumer revisions in private evidence. Validate edge auth/CORS/cookies/raw Stripe bytes/SSE, then reopen admission and resume only the matching Neon workers/schedules.
5. Once the Function path is repaired, repeat the same gated upstream change back. Keep rollback retention/billing explicit; do not add a permanent warm API service. Destroy temporary acceptance hosts only after the owner agrees the required retention evidence remains available.

Before **any new writes/auth adoption**, a coordinated rollback may restore all old consumers to the old authoritative database. After writes/auth adoption, fallback must use current Neon state; changing databases requires reconciling every write and retaining every Neon-only identity first. No runtime migration, account remapping by email, automated database deletion, or fallback to an owner role is permitted.
